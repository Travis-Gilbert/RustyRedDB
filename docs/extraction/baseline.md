## Repair baseline procedure

The exact plan pin was materialized from Git into an isolated source snapshot, never from a live personal database. The core and query source suites were executed with the pinned Rust 1.96.1 compiler and locked source dependency graph. Candidate checks use their own target directory. A run is recorded only after completion.

`source-parity.json` records hashes of exact blobs at both the plan pin and the historical Cursor extraction source, alongside candidate bytes. It is generated by `scripts/source_parity.py --source-repository PATH --output docs/extraction/source-parity.json`; the private source/history is not copied into this repository. Differences retained from the extraction source are reviewed separately from the repair changes.

The pinned source retains the physical log/fold implementation separately from RedCore. Extraction did not authorize dropping that owner or replacing its durability with graph snapshots. See [storage-owners.md](storage-owners.md).

## Timing-oracle profile

The retained `memory_document_query_latency_fixture_records_delta` was introduced
in Theorem `36a86b66c2c927ae166e3bd1a86b195e137f837a` with 512 documents,
250 iterations, and a 191,312 ns/query ceiling. At that commit the workspace
development profile had `opt-level = 1`; the test profile inherited it. Theorem
`56c312e7af24a7410a6e222a7e1b67bc74dbefc0` later changed development optimization
and introduced the separate optimized `dev-run` profile.

The first repair CI run, `39483629328`, used Cargo's unoptimized default and
failed this oracle on both hosts (200,296 ns/query on macOS; 423,086 on Linux).
These remain failures. The standalone test profile now explicitly uses
`opt-level = 1`, preserving the original oracle's runtime optimization and its
unchanged ceiling. This is profile provenance, not a claim of bit-identical
historical builds or a universal cross-machine performance guarantee. Candidate
results must still pass the retained test; they are recorded separately.

The four source unit failures are three browser-projection tests that open a
second writer while retaining the first, and the document-query timing ceiling
under the source's unoptimized root profile (2,101,779 ns/query versus 191,312).
The integration failures are the hook storm's scheduler-dependent debounce
(2 calls versus 1), the stale mixed-vector fallback assertion, and a child
ACK line joined to libtest's serial test-name prefix. These are observed
baseline failures, not inferred explanations for unexecuted checks.

Candidate repairs preserve the hook oracle's 50 separate real commits and
one-call assertion while explicitly gating dispatch until the storm is queued.
The floor crash test places ACK on its own stdout line; crash/reopen assertions
and kill stages are unchanged. Vector assertions retain indexed-node/backend
checks and independently read each label's counters before aggregate fallback.

The bounded-commit ratio was calibrated separately: its introduction in
`9ee2a2798c` and the frozen source use root optimization 0 and dependency
optimization 2. An additional exact-source execution captured commit median
25.145417 ms, full-attribution/serialization 43.511292 ms, ratio 0.58 (ceiling
4.0). Candidate root optimization 1 made the commit faster (12.384 ms) but the
reference traversal much faster (2.985875 ms), yielding 4.15. The relevant
in-memory commit, graph, footprint, and attribution implementations are byte
identical to the plan pin. The normal gate therefore runs all integration
targets with the calibrated development profile, and units with test-root
optimization 1; both retain dependency optimization 2. Neither timing ceiling
is raised or removed. These are reproducible profile-bound oracles, not a
cross-machine speed claim.
